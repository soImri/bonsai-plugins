# Adding a connector to Connector cards

Connector cards gives a connected app its own UI inside Bonsai's chat. The person asks in words, the plugin reads the app through Bonsai's sign-in, Jev picks which screen and which fields fit the ask, the card renders, and edits write back through the same sign-in. Linear and Google Calendar are the first two connectors; this document is the process that produced the second one and is how the third gets added.

## How it is put together

```
runtime.ts                 four generic tools (cards_view / record / draft / apply), connector routing,
                           sign-in resolution, Jev (8-question cap, shrinking rubric), the follow-up picker,
                           recipes (remembered compositions per similar ask, scored on the next move),
                           the pick log (picks, offered/used follow-ups, corrections), cache
connectors/index.ts        the registry (agent side)
connectors/ui.ts           the registry (UI side)
connectors/<id>/
  index.ts                 defineConnector({ id, label, summary, aliases, auth, triggers, examples, filters,
                                             view, record, draft, apply })
  api.ts                   the app's calls, normalised records, cached pick lists
  rubrics.ts               what Jev is asked, most important first, plus heuristic twins; the follow-up candidates per screen
  write.ts                 the card grammar parser (Save …: field → value; Create …: title + properties)
  ui.tsx                   the compositions, drawn from ui/kit.tsx, exported as a ConnectorUi
  SCREENS.md               the screen map (which screens, which fields, what edits, what a Save writes)
  evals.json               parse cases (offline) and live cases (the real tool, no model)
ui/kit.tsx                 card chrome, Picker, SaveBar, glyphs, useFollowUps (additive follow-ups), the ConnectorUi contract
ui/entry.tsx               the UI shell: one renderer per tool, dispatching by details.connector
kay-ui.tsx                 GENERATED by tools/build-ui.mjs from ui/ and connectors/*/ui.tsx; the manifest's UI entry
tools/new-connector.mjs    the scaffold;  tools/eval.mjs  the eval runner;  tools/build-ui.mjs  the UI build;  tools/template/  the template
skills/                    connector-cards (the agent's one-page routing) and add-connector (this process, short)
```

The runtime routes a call to a connector in this order: the `connector` argument; a record reference the connector's `refPattern` recognises (NEAT-9, #a1b2c3); a card message its `messagePattern` claims; keyword hits in the task (ties go on); the only connector; Jev asked to choose among the connectors' summaries. So a connector declares how to recognise its asks and never sees another connector's.

## The process, in order

Each step leaves an artifact the next step uses.

**1. Inventory: what can Bonsai reach?** Before any design, find the data route and the sign-in ids. `read plugin://<the app's plugin>` and `help <scheme>://` show what Bonsai already reads and writes and which service/scheme its sign-in uses. `read mcp://<server>` lists the app's MCP tools when it ships a server; sometimes that is the only surface the token accepts (Linear's token is refused by its GraphQL API; Google's works on REST). Write the route into the top of `SCREENS.md`.

The plugin reaches the app through a *shared-identity* grant: the manifest declares `{service, schemes, operations: ["resolve"]}` under `permissions.byTarget.kay.agent.auth`, and the person grants `auth.shared-identity` for that service on the plugin's install row. Every declared service must be granted or the whole agent target is refused, so declare only what you ship.

**2. Screen map.** Pick the three to five screens people have muscle memory for. The card is one surface the person navigates inside: every chip, tab, row and expander acts on data the card already holds. A control that would need another tool call does not belong in the card; either the read fetches a superset up front (two weeks of Slack with replies, a month of calendar either side, every issue of the team) or the control is left out until the lazy-load route (layer 2, the endpoint bus) exists. The only clicks that leave the card are writes (Save, Send, Create, RSVP, React), and those redraw the same card from the app's truth. Two sources beat online research: the app's own screens (open it in the browser pane) and the person's actual asks (`search sessions://` for the app's name). One table row per screen: screen → composition → fields shown → fields that edit → what a Save writes → what changes for chat. Rules that hold for every card: it mimics the app's UI, never a form of fields; edits batch behind Save, no write per click; one record per card when the ask names one; no navigation chrome.

**2b. Follow-ups: the screen's own controls are always live; a follow-up only adds.** Every control the mimicked screen has is drawn and interactive on every card, exactly as the app has it: pickers pick, tabs switch, rows edit, composers send. Never a disabled, read-only or dimmed version of a control, never a disclosure that hides one (the "More" chip of 0.8.0 and the read-only pills of 0.9.0 were both wrong and are gone). A *follow-up* is an additive secondary action the card gains for this ask: the comment box already open on an issue the person is answering, a `+ New issue` button on a list they are planning from, a `+ New event` button on an agenda they want to block time in. Candidates live in the connector's `rubrics.ts` as `FollowUp[]` (`{ id, label, when, unless?, guess, always? }`), few per screen; `index.ts` passes them to `run.followUps(purpose, state, candidates)`, which asks Jev one bool per candidate *in parallel with the composition rubric* (same wall time), judging the ask, the agent-supplied `context` and the record of similar asks. The payload carries the picked ids (`composition.followUps`, `followUps`); the UI reads them with `useFollowUps(ids).picked("id")` and adds the control when picked. A screen with nothing worth adding has no candidates (Slack today).

**2b′. Navigation is tailored; the screen is not.** Two layers in every list-type card. The *screen* (rows, pills, composers, click-to-edit, Save) is the app's own and is always complete and live. The *navigation row* (our range chips, scope tabs, focus filters) is Connector cards' adaptation, and it is cut to the ask: the asked range or scope plus its neighbour ("next week" → This week · Next week; "what's open" → Open · In progress), peripheral information only when it exists ("Invites · 2" only with pending invitations), and whatever Jev adds for the ask (Find a time, Month, + New event). The full set, the connector's *golden* navigation, is drawn only when the ask is a general look ("show my calendar", "my Linear", "catch me up on Slack"), decided by a `full_navigation` candidate in the follow-up rubric and remembered by the recipe. The connector computes the set in `rubrics.ts` (`chipsFor`, `scopesFor`, `inboxChips`) and puts it on the composition (`chips`, `scopes`, `focuses`/`ranges`); the UI draws exactly that, every chip live. A row with one chip is not drawn: the heading already names the range.

**2c. Memory: a similar ask is solved from its recipe, not composed again.** The runtime keeps *recipes* (`<dataDir>/recipes.json`): for each connector and kind, the asks it has solved (their words and the context's words), the composition it drew, the follow-ups it offered with how often each was used, and a record: `uses`, `successes` (the person's next move was covered by what the card offered) and `misses` (they needed a control the card did not have). On a call, the closest recipe (word overlap of the ask ≥ 0.6, of the context ≥ 0.3) is recalled. With two or more uses and a clean enough record (no misses, or ≥ 70 % covered) it is reused as is: `remembered(recall, () => jev(...))` returns the composition with `by: "memory"` and `run.followUps` returns the recipe's top follow-ups, no Jev call. Otherwise Jev decides, with the recipe's record in its state, and the recipe is re-learned from that decision (its counters reset). Success and miss are read from the person's next move: done on the card (a Save, Send, Create from its own controls) is a success; typed in words (the agent writes through `cards_apply { payload }`) is a miss, and the move is mapped onto a candidate control (via the candidate's `covers`) so the recipe offers it next time. Draft property picks (which project, which priority) depend on the content and are never remembered; a draft's follow-ups are. Connectors return `remember: comp` from `view` and `remember: { by }` from `record`/`draft` so the runtime knows who decided.

**3. Scaffold.** `node tools/new-connector.mjs <id> "<Label>" <serviceId> <schemeId>`. It creates the folder from the template, registers the connector on both sides, adds the sign-in to the manifest, and prints the grant the person must add. Fill the TODOs top to bottom.

**4. Reads, rubrics, writes, compositions.**

- `api.ts`: bearer calls; normalise to one plain record shape; cache pick lists for 10 minutes, stale-while-revalidate. Long opaque ids get a short stable key (`#a1b2c3`) so cards can name records in plain words; remember every key a card could send back.
- `rubrics.ts`: at most 8 questions, most important first (the hosted Jev route refuses more; the runtime drops the tail on a 400). Choice criteria keys are plain tokens (`p0`, `s1`) mapped back after the answer. Every answer has a heuristic twin, so a dropped question degrades gracefully. Put `pastPicksForSimilarAsks` (the runtime's `history`) in the state.
- `write.ts`: the card speaks a short human grammar in the chat; the agent passes the message verbatim. Unit-check the parser with the eval runner before wiring it.
- `index.ts`: `apply` re-reads what it touched and returns a view or record payload, so the card redraws from the app's truth. Return `picked` (one line) from view and draft, and `correction` from apply when the person changed what the draft proposed; the runtime logs both.
- `ui.tsx`: read `ctx.details`, send with `ctx.send`, open links with `ctx.openUrl`. Compositions are components; the connector's entry switches on `details.kind`. Then `node tools/build-ui.mjs`: Bonsai bundles a plugin's UI entry from its text in a virtual folder, so `kay-ui.tsx` must be one file; the script builds it from `ui/entry.tsx` and every connector's `ui.tsx` (esbuild, found locally or via npx) and you commit the output. Forgetting this leaves the previous cards running: the daemon reports the UI part as active while the app log says `Could not resolve "./ui/kit.tsx"`.

**5. Eval set.** `evals.json` holds parse cases (`{ parse, expect }`, run offline) and live cases (`{ ask, tool, args, expect }`, run through the real tool with the `kay` CLI, no model turn; never apply). `node tools/eval.mjs <id>` from an agent's Bash, or with `--session <id>` from a terminal. Expectations are dotted paths into the result's details: `"composition.view": "list"`. Keep it green; it is the regression gate when a rubric's wording changes.

**6. Test like a person.** Build the UI first (`node tools/build-ui.mjs`), then commit: a git commit in the plugin directory reloads the plugin (touching files does not; toggling the install does not). Subagents keep the parent's plugin generation, so test in fresh top-level sessions and read their transcripts: one tool call and no reads before it, the expected connector, the composition Jev picked, the timing, and the card message round-tripping through `cards_apply`. Then look at the cards yourself; the agent cannot see them.

**6b. Visual QA without the app.** The agent cannot see a rendered card, so gestures and layout get checked in a browser harness: `~/bonsai-ui-demo/freetime.html` + `src/freetime.tsx` (Vite on port 5177, `@bonsai/plugin-ui-sdk/ui` aliased to the vendored `@bonsai/ui`) renders a connector's `ui.tsx` with fixture details and drives synthetic pointer events through buttons whose results print under the card; open it in Bonsai's browser pane and read the log. Copy the pattern for any card whose behaviour the evals cannot reach (drag, resize, hover, keyboard).

**7. The loop.** Two stores. `picks.json`: every pick, the follow-ups offered, the `context` the agent passed, which follow-ups the person then used (from the apply messages), who decided (`jev`, `memory`, `fallback`), and for drafts what the person changed before confirming; the last few for similar asks go into Jev's state. `recipes.json` (2c): the remembered solutions with their success record, scored on the person's next move. A card that keeps covering the next move stops costing a Jev call; one that misses gets re-learned. The last few picks for similar asks are fed into the rubric's state as `pastPicksForSimilarAsks`, so Jev sees what this person chose last time without any rubric edit. When the log shows a rubric wording consistently losing, change the wording and let the eval set say whether the change holds.

## What Google Calendar cost

The second connector, built with this process on 2026-10-23: inventory and screen map 15 minutes; api/rubrics/write/index about 350 lines; ui.tsx about 220 lines; evals 10 cases; two fresh-session tests. The things that bit: the Google sign-in needed the calendar scope granted once (`service_connect gcal`), and a freshly created event's key had to be remembered before a card could delete it.

## Known limits

Bonsai's structured card-action channel is reserved for its own `ui_render` cards, so a card's Save is a plain chat message the person can read. The agent cannot see rendered cards. The hosted Jev route takes 8 questions per call. One shared-identity grant per service, all required.
